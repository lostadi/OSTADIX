Primary compiler objective

The highest compiler priority is for olangc to fully and automatically compile existing external runtime and compiler implementations in terms of O-core. General support for arbitrary implementations is the architectural objective; do not restrict it to a fixed language list or interpreter-only tier. Preserve the original language engines without requiring manual language-runtime reimplementation.

olangc must own the source/build recipe, frontend invocation, O-core import, verification, ABI adaptation, dependency resolution, linking, and artifact construction. The result bundles the compiled runtime/compiler, .O program, foreign scripts, and complete declared dependency closure in native binary form, a complete verified O-core IR artifact, or a complete OIR program artifact for later native lowering. OIR may contain the orchestration and verified native O-core modules together, with explicit linkage, scripts, resources, execution profile, and provenance. Native module references must resolve within the included dependency closure. All forms must preserve observable semantics across every ISA in which O-core is implemented. x86-64, AArch64, and RV64GC remain mandatory minimum targets. In this objective, "bundling runtimes with scripts" means this compiled whole program, not merely embedding supplied executable files.

Completeness includes required functions, globals, initializers, relocations, ABI features, libraries, compiler helpers, modules, and explicit platform interfaces. Partial imports and feature-census percentages do not establish complete runtime/compiler support. Report current coverage and unsupported constructs honestly; the universal objective is not a claim of present support.

Embedding a supplied runtime executable, generating O-core source from a polyglot block, or shipping an interpreter for an unchanged imported IR is not evidence that the external runtime itself was lowered through O-core. Report those mechanisms accurately. Keep OIR/ExecutionPlans and O-core MIR distinct and connect them through explicit runtime/operation interfaces. This separation of internal invariants does not forbid a complete OIR artifact from containing the native modules and their realization bindings. Foreign scripts may remain interpreted by the O-core-compiled language runtime. Compiler self-hosting is a separate objective. Compiling a compiler implementation and routing the programs it generates through O-core are distinct required capabilities of the overall design. Reuse existing implementation-language frontends and build metadata to make the import general. Manual runtime rewrites and O-core text staging do not satisfy the requested automated foreign-runtime/compiler lowering objective. Keep lowering and replayability separate. Preserve imported semantics and qualify cross-ISA equivalence per execution profile; do not infer purity from a runtime name. JIT implementations remain in scope, with generated-code lowering and publication requiring their own explicit supported path.

Primary runtime-lowering acceptance tests

Lee explicitly identifies O-core's ability to lower any original language-runtime implementation as its most important property. Design the primary acceptance tests around that full, extensible pipeline, alongside the other required mechanisms. Drive unchanged, pinned upstream runtime/compiler sources and their declared build metadata through olangc-owned frontend invocation, complete O-core import and independent verification, ABI/dependency/provider resolution, complete artifact construction, and reference-versus-owned observable behavior for each declared ISA/execution profile. Reuse producer contracts and profile data; do not turn the named languages into a whitelist or substitute manually rewritten runtimes.

Keep compiler-body lowering, compiler-generated program routing, and JIT code lowering/publication/invalidation as explicit distinct gates where applicable. Test complete native, verified O-core IR, and complete OIR artifact contracts according to their actual delivery form; do not confuse OIR orchestration with lowered runtime bodies. Foreign programs may be interpreted by the original O-core-compiled language engine. An interpreter for unchanged imported implementation IR is not runtime-lowering proof.

Include negative controls for missing required units/functions/globals/initializers/providers/resources, unresolved native references, ABI/target mismatches, opaque supplied-runtime executable embedding, unverified/partial modules, and unsupported generated-code paths. Retain exact failures. Passing capture, registry, rejection, feature, or ABI unit tests must not mark original-runtime acceptance complete. Missing prerequisites or unsupported required profiles remain explicit unmet acceptance results, never silent skips or a passing zero-case suite. Preserve the remaining ISA, semantic, source-ownership, replayability, and platform-interface requirements.
