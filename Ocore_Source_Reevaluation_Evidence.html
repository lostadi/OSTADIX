O-core source reevaluation evidence

O-core owns the intermediate representations and native assembly generators used by its .oc compiler. It is not a syntax frontend that delegates that route's native code generation to LLVM. LLVM also has an implemented, separate role in foreign-code import. Backend ownership, graph-level dependency checks, and preservation of those relationships in native execution are separate claims.

Here, verified in source means confirmed in the inspected implementation. It is not a proof that every accepted program compiles correctly. Execution evidence must identify the tested inputs, compiler, target and execution profile.

Native O-core source

.oc source -> parsed AST -> typeck::check -> typed HIR -> mir::lower
           -> typed SSA MIR -> O-core target assembly -> assembler -> ELF object

ocore::driver::compile_with_function_sections calls the parser, checker and lowering passes in that order. Its target match selects the x86-64, AArch64 or RISC-V generator. emit_object subsequently invokes Clang as an assembler. These are distinct compiler and assembler stages. Assembler encoding, pseudo-instruction expansion and any permitted relaxation remain separate responsibilities; owning target assembly emission does not mean that the external assembler or linker is absent from the toolchain.

ocore::mir represents each temporary as an SSA ValueId with one defining instruction. Mutable locals and statics are explicit Places; a load produces a new SSA value. This preserves the distinction between a value definition and the mutable storage from which it was obtained.

The x86-64, AArch64 and RV64 generators construct assembly from HIR/MIR. For example, x86-64 emits statics and processes MIR functions through its own FunctionCodegen; it does not call an LLVM object emitter.

Imported implementations

whole foreign LLVM module -> pinned LLVM parsing and verification
                         -> O-core NativeModule -> independent verification
                         -> O-core ISA assembly -> assembler -> ELF object

ocorec accepts --input-kind llvm-ir, invokes its embedded import worker and passes the resulting native module to the native driver. ocore_llvm_import.py uses the digest-pinned LLVM C API and the accompanying bitcode audit. This is an implemented import route, rather than a census or an implicit property of .oc syntax.

NativeModule retains imported types, target layout, ABI, symbols, control flow, instructions and provenance. native_verify verifies that representation independently. native_codegen audits the complete module's supported native realization before emitting its own target assembly. Imported semantics remain distinct from .oc semantics. Unsupported features fail explicitly; partial lowering does not qualify a complete implementation.

The object inventory also checks actual ELF storage, symbols, fixups and owned exception metadata. In particular, valid RISC-V difference-relocation pairs must describe the exact owned FDE extent, CFI advance or LSDA field. The checker does not treat duplicate offsets as sufficient evidence and rejects changed endpoints even when their numeric difference is unchanged. These checks establish owned field geometry; they do not qualify an unwinder or executed CFA recovery.

The parser pin is also a real environment requirement. The current importer requires LLVM 22.1.6 and the admitted library digest. Having Clang 19 or a Rust compiler installed does not establish that the foreign import route works on that host. An explicitly supplied library still has to pass its digest, version and C API checks. The checks must not be weakened to manufacture a successful runtime result.

The hosted .O binary target is another distinct path: olangc generates a Rust evaluator project and invokes Cargo. Producing that hosted native executable does not establish an OIR-to-O-core orchestrator. The two O-core native routes above must not be conflated with hosted evaluator packaging.

Implemented graph and provenance relationships

hgraph::from_oir projects the validated execution plan into executable hyperedges with separate value, completion, control, actor and resource-state inputs and outputs. Resource tracking includes state versions and reader drains. The readiness scheduler uses these relationships as execution blockers; they are operational constraints.

evidence::admit checks exact program, plan, solved graph and runtime bindings before constructing the private admitted-execution type accepted by the coordinator. Current V6 admission materializes type, effect, dispatch, capability, placement, failure and resource-demand evidence. Descriptive inspection snapshots and historical receipts do not authorize a fresh execution.

information_provenance also implements admission against the exact execution admission, signed receipt and terminal output. Its guarantees are those checked bindings; they do not automatically extend to arbitrary native instructions or all external effects.

The project-specific planning and execution path has its own source-plan reconstruction and terminal runtime-graph evidence. The executor specification describes the limits between these execution and admission paths.

Bounded native execution beneath the admitted graph

The ordinary .O builtin ocore_i64 now connects a static, embedded NativeModule to an executable graph edge. Its adapter independently verifies the whole module and audits every function and block, including unused definitions. The admitted profile consists of defined C-ABI i64 functions, integer SSA and acyclic control flow. Memory, globals, external calls, aliases and runtime hooks reject. An imported llvm.trap declaration is retained as metadata for the explicit trap operation. Register and stack arguments use the target ABI.

Before fresh execution admission, the adapter emits owned assembly, adds its fixed Linux framing wrapper, and invokes the selected assembler and static linker. Its manifest binds the descriptor, normalized module, assembly, adapter executable, exact tools, flags, captured working directory and tool environment, and generated ELF. The tool executables and resulting ELF are retained as sealed Linux file descriptors. Tool dynamic dependencies remain part of the trusted host toolchain; these hashes do not establish a complete independently lowered toolchain closure.

The executable lease set checks that the leaf inventory and arities match the source plan. Admission and dispatch reuse those prepared leases. Dispatch receives graph-ready values, requires signed i64 integers or canonical decimal text, and returns through normal semantic settlement. Invalid arguments and native traps are failures; they cannot publish a native result or unblock a dependent Store. The source descriptor, plan node and executable edge participate in the existing hashes and admission checks.

The CLI's --json execution evidence exposes the admitted native inventory, actual node events and successful value, completion and resource publications, including on failed runs. An admitted leaf record alone does not establish that it ran; the trace establishes observed execution. This is a native leaf under the existing Rust coordinator. General native graph orchestration, effectful native resource handles and instruction-level debugging remain separate requirements. The interface documentation gives the descriptor format and a complete ordinary .O example.

Imported binary128 storage and narrow return compatibility

The LLVM importer and independent native emitter now admit IEEE binary128 as storage with exact 16-byte allocation and alignment. This permits original aggregate layouts, alloca/GEP, raw copies and exact positive-zero initializers, including packed fields. It does not admit binary128 arithmetic, scalar loads/stores, SSA transport or floating-point call classification. Other 128-bit floating formats remain distinct, and changing a declared layout does not bypass the emitter's independent checks.

An ordinary direct C i32 call also has one explicit target-specific refinement: a callee's signext return guarantee can satisfy a bare caller on the admitted 64-bit ELF ABIs. Both original attribute vectors remain in the IR. The owned caller consumes the low 32 bits, while the callee retains its original return plan. Reverse guarantees, zeroext conflicts, parameter changes, aliases, Invoke and provider-signature equality remain strict. The importer rejects musttail before constructing this ordinary call. This is a deliberately narrow native rule: LLVM 22's ABI documentation generally requires ABI attribute agreement and does not license arbitrary signature mismatches.

Native assembly provenance added in this work

native_map records the exact half-open UTF-8 assembly byte ranges for imported native instructions, terminators, block labels, prologues, epilogues and exception-landing stubs. Zero-width compiler markers and PHIs remain represented. Predecessor terminators own their lowered PHI copies; exception-landing sites own unwind-edge copies.

The map binds the target, normalized typed module and generated assembly. The driver additionally binds and embeds the exact imported module-file bytes and binds the final artifact. The embedded snapshot can be recovered even when LLVM import used a private temporary; it does not require a later import to reproduce incidental metadata printer provenance. Verification re-verifies the module and regenerates every assembly site, then checks the supplied artifact's digest. A matching object digest identifies the declared bytes in an unsigned sidecar; it does not independently prove assembly-to-object correspondence, assembler correctness or execution semantics. An object replacement accompanied by a changed declared digest is outside that descriptive identity check. Assembly replacement, even with changed hashes, rejects when it differs from regenerated O-core emission.

This is a descriptive compiler correspondence for imported native IR. It does not supply .oc source spans, machine-address ranges, a debugger, native HGraph dispatch, runtime observations or admission authority. Existing plain emission shares the same emitter and remains byte-identical.

Direct original-source recipe orchestration

olangc --native-runtime now accepts an original-source build recipe directly. With --native-runtime-source, it invokes its embedded capture worker, independently re-verifies the resulting build evidence, and passes the admitted whole units to the existing O-core lowering route. The caller supplies the clean pinned checkout, exact frontend tools and admitted LLVM parser; the compiler creates a separate new build/capture/lowering directory. Existing output directories, output paths within the source checkout (including aliases), and escaping inventory paths reject before they can be reused.

The source-recipe receipt binds the recipe, embedded worker/helper, capture report and lowering evidence by exact bytes and SHA-256. Capture completion requires independent replay admission; successful reference builds alone do not set it. Failure retains the stage, process arguments, diagnostics and any admitted evidence. Complete unit lowering remains separate from a complete runtime, dependency closure, linking and native execution qualification. The workflow documentation and unchanged Lua recipe describe the commands and their current limits.

The direct-source development evidence records 11 passing CLI cases with native fixture execution, 17 passing existing capture/package cases, and the unchanged Lua invocation. Lua captured and independently admitted all 34 units, then stopped before any unit import because its declared source dependencies lacked verified included module-sets. Its Clang-built reference engine passed the smoke test; it is not an O-core native Lua product.

What is still required for the broader completion claim

The compiler now also writes and consumes self-contained ocore-native-module-set-v1 packages. The package verifier re-verifies every embedded module, target/profile binding, component/unit inventory, dependency edge and symbol/ABI/COMDAT closure. Direct package input can produce IR or owned objects without reopening original source, LLVM or capture files. This closes a concrete artifact and dependency-composition gap; it does not supply scripts, platform/resource closure, executable linking or native HGraph dispatch.

The original Lua recipe captures the whole pinned upstream Make configuration. The committed recipe now also passed with actual Clang/LLVM 22.1.6 on this RISC-V host: 34 LLVM units, 33 archive members and 111 source/data files, independent capture verification, and original-engine reference smoke. The SDK evidence records Debian signed-index/package verification, the exact library hash, required C-API health, and a scalar imported module's owned-object execution.

The whole-unit Lua diagnostic attempted all 34 original units: 5 reached independently verified O-core IR and owned RISC-V objects; 29 rejected. First diagnostics identify floating-point types, variadic interfaces and an unsupported symbolic initializer. These are complete unit outcomes, not percentages of engine support. The separate full-runtime route rejects missing verified library/platform dependency module-sets before unit import. Neither the original Clang-built executable nor these partial imports establish complete O-core lowering or runtime dependency closure.

The acceptance requirements in OCORE.md distinguish source capture, complete lowering, dependency closure, linking and native execution. An original runtime or compiler must pass through the owned emitters with every required function, global, initializer, relocation, ABI feature, helper, library and module accounted for. Its build must bind the exact source, configuration, frontend, IR and artifacts. Scripts and declared resource closure must be included, with native references resolving to verified content.

The bounded native leaf above provides one explicit interface between the ExecutionPlan, owned native computation and semantic publication. A general OIR/ExecutionPlan-to-O-core runtime interface must extend that preservation to the required effects, resource handles and orchestration. Carrying a graph, bundling an unchanged runtime executable or calling a hosted evaluator does not establish that general lowering.

Reference tests and real .O execution must compare required values, faults and effects on x86-64, AArch64 and RV64GC under explicit execution profiles, after removing dependence on the original runtime executable. Linux hosts and QEMU user-mode runs provide development evidence; native OSTADIX service acceptance and physical-device claims require their own gates. Compiling a compiler implementation and routing its generated programs through O-core are separate requirements. JIT code publication also needs a verified path.

The stronger architectural claim is therefore precise: ownership of the native backend makes additional relationships representable and checkable. The source already implements substantial graph and provenance checks. Complete preservation through native execution remains an independently testable obligation, not a consequence of backend ownership alone.
