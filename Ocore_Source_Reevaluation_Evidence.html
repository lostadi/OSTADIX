O-core source reevaluation evidence

O-core owns the intermediate representations and native assembly generators used by its .oc compiler. It is not a syntax frontend that delegates that route's native code generation to LLVM. LLVM also has an implemented, separate role in foreign-code import. Backend ownership, graph-level dependency checks, and preservation of those relationships in native execution are separate claims.

Here, verified in source means confirmed in the inspected implementation. It is not a proof that every accepted program compiles correctly. Execution evidence must identify the tested inputs, compiler, target and execution profile.

Native O-core source

.oc source -> parsed AST -> typeck::check -> typed HIR -> mir::lower
           -> typed SSA MIR -> O-core target assembly -> assembler -> ELF object

ocore::driver::compile_with_function_sections calls the parser, checker and lowering passes in that order. Its target match selects the x86-64, AArch64 or RISC-V generator. emit_object subsequently invokes Clang as an assembler. These are distinct compiler and assembler stages.

ocore::mir represents each temporary as an SSA ValueId with one defining instruction. Mutable locals and statics are explicit Places; a load produces a new SSA value. This preserves the distinction between a value definition and the mutable storage from which it was obtained.

The x86-64, AArch64 and RV64 generators construct assembly from HIR/MIR. For example, x86-64 emits statics and processes MIR functions through its own FunctionCodegen; it does not call an LLVM object emitter.

Imported implementations

whole foreign LLVM module -> pinned LLVM parsing and verification
                         -> O-core NativeModule -> independent verification
                         -> O-core ISA assembly -> assembler -> ELF object

ocorec accepts --input-kind llvm-ir, invokes its embedded import worker and passes the resulting native module to the native driver. ocore_llvm_import.py uses the digest-pinned LLVM C API and the accompanying bitcode audit. This is an implemented import route, rather than a census or an implicit property of .oc syntax.

NativeModule retains imported types, target layout, ABI, symbols, control flow, instructions and provenance. native_verify verifies that representation independently. native_codegen audits the complete module's supported native realization before emitting its own target assembly. Imported semantics remain distinct from .oc semantics. Unsupported features fail explicitly; partial lowering does not qualify a complete implementation.

The parser pin is also a real environment requirement. The current importer requires LLVM 22.1.6 and the admitted library digest. Having Clang 19 or a Rust compiler installed does not establish that the foreign import route works on that host. An explicitly supplied library still has to pass its digest, version and C API checks. The checks must not be weakened to manufacture a successful runtime result.

Implemented graph and provenance relationships

hgraph::from_oir projects the validated execution plan into executable hyperedges with separate value, completion, control, actor and resource-state inputs and outputs. Resource tracking includes state versions and reader drains. The readiness scheduler uses these relationships as execution blockers; they are operational constraints.

evidence::admit checks exact program, plan, solved graph and runtime bindings before constructing the private admitted-execution type accepted by the coordinator. Current V6 admission materializes type, effect, dispatch, capability, placement, failure and resource-demand evidence. Descriptive inspection snapshots and historical receipts do not authorize a fresh execution.

information_provenance also implements admission against the exact execution admission, signed receipt and terminal output. Its guarantees are those checked bindings; they do not automatically extend to arbitrary native instructions or all external effects.

The project-specific planning and execution path has its own source-plan reconstruction and terminal runtime-graph evidence. The executor specification describes the limits between these execution and admission paths.

Native assembly provenance added in this work

native_map records the exact half-open UTF-8 assembly byte ranges for imported native instructions, terminators, block labels, prologues, epilogues and exception-landing stubs. Zero-width compiler markers and PHIs remain represented. Predecessor terminators own their lowered PHI copies; exception-landing sites own unwind-edge copies.

The map binds the target, normalized typed module and generated assembly. The driver additionally binds the exact module-file bytes and final artifact. Verification re-verifies the module and regenerates every assembly site, then checks the supplied artifact's digest. A matching object digest identifies the declared bytes in an unsigned sidecar; it does not independently prove assembly-to-object correspondence, assembler correctness or execution semantics. An object replacement accompanied by a changed declared digest is outside that descriptive identity check. Assembly replacement, even with changed hashes, rejects when it differs from regenerated O-core emission.

This is a descriptive compiler correspondence for imported native IR. It does not supply .oc source spans, machine-address ranges, a debugger, native HGraph dispatch, runtime observations or admission authority. Existing plain emission shares the same emitter and remains byte-identical.

What is still required for the broader completion claim

The compiler now also writes and consumes self-contained ocore-native-module-set-v1 packages. The package verifier re-verifies every embedded module, target/profile binding, component/unit inventory, dependency edge and symbol/ABI/COMDAT closure. Direct package input can produce IR or owned objects without reopening original source, LLVM or capture files. This closes a concrete artifact and dependency-composition gap; it does not supply scripts, platform/resource closure, executable linking or native HGraph dispatch.

The original Lua recipe captures the whole pinned upstream Make configuration. A genuine diagnostic capture with Clang 19.1.7 retained 34 LLVM units, 33 archive members and 111 source/data files; independent capture verification and original-language reference smoke passed. That diagnostic capture is explicitly distinct from the committed recipe's LLVM 22.1.6 requirement and from O-core lowering of the complete engine.

The acceptance requirements in OCORE.md distinguish source capture, complete lowering, dependency closure, linking and native execution. An original runtime or compiler must pass through the owned emitters with every required function, global, initializer, relocation, ABI feature, helper, library and module accounted for. Its build must bind the exact source, configuration, frontend, IR and artifacts. Scripts and declared resource closure must be included, with native references resolving to verified content.

An explicit OIR/ExecutionPlan-to-O-core runtime interface must then preserve the admitted value, control and resource relationships at native dispatch and result publication. Carrying a graph, bundling an unchanged runtime executable or calling a hosted evaluator does not establish that lowering.

Reference tests and real .O execution must compare required values, faults and effects on x86-64, AArch64 and RV64GC under explicit execution profiles, after removing dependence on the original runtime executable. Linux hosts and QEMU user-mode runs provide development evidence; native OSTADIX service acceptance and physical-device claims require their own gates. Compiling a compiler implementation and routing its generated programs through O-core are separate requirements. JIT code publication also needs a verified path.

The stronger architectural claim is therefore precise: ownership of the native backend makes additional relationships representable and checkable. The source already implements substantial graph and provenance checks. Complete preservation through native execution remains an independently testable obligation, not a consequence of backend ownership alone.
