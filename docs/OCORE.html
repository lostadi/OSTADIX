O-core Language and Freestanding Runtime Specification

Status: draft v0.1, normative for the ocorec implementation.

The separate native Ethernet and real Linux integration profiles describe the new executable QEMU paths and their remaining distributed-authority and physical-device requirements.

O-core is the native systems-programming member of O-lang. It is deliberately separate from the polyglot orchestration language and its OIR. O-core programs are statically typed and compile ahead of time to target object files. Foreign language blocks (python^, rust^, and similar) are hosted facilities and are never available in freestanding O-core code.

1. Compilation model

The native pipeline is:

O-core source -> AST -> resolved, typed HIR -> SSA MIR -> target object

The existing orchestration pipeline remains:

.O source -> ONode -> OIR execution plan -> hosted evaluator/backends

OIR and O-core MIR are different representations with different invariants. OIR models dependency and backend execution. MIR models typed machine-level computation. Neither is implicitly converted to the other. This internal separation does not prevent a future complete OIR artifact from containing verified native O-core modules and explicit realization bindings.

Supported native targets are x86_64-unknown-none, aarch64-unknown-none, and riscv64-unknown-none (RV64GC). All emit target assembly and little-endian ELF64 objects with an LP64 data model. extern "C" selects the target's integer C calling convention: System V AMD64, AAPCS64, or RISC-V LP64. The default compiler-versioned extern "ocore" convention uses the corresponding scalar register and stack placement. Explicit extern "sysv64" remains AMD64-only.

The .oc backends share typed HIR/MIR. A separate verified native-module IR now accepts a bounded LLVM import profile, including actual C and Rust frontend output, and has O-core-owned assembly emitters for all three ISAs. It preserves the existing .oc semantics rather than assuming that foreign code shares them. This bridge does not yet compile a complete external runtime or compiler.

External runtime lowering and script bundles

The primary compiler objective is for olangc to fully and automatically compile existing external runtime and compiler implementations in terms of O-core, preserving their original language engines. Support for arbitrary implementations is the architectural objective, including interpreters, ahead-of-time compilers, and JIT runtimes. This is a required development direction, not an implemented external-runtime compilation feature. olangc must own source/build recipes, frontend invocation, import, verification, ABI adaptation, dependency resolution, linking, and artifact construction. The intended pipeline is:

runtime/compiler implementation source -> frontend/importer -> verified O-core IR/MIR
.O source -> OIR/ExecutionPlan + foreign scripts
O-core modules + orchestration + scripts + adapters + dependency closure
        -> complete OIR program artifact (or native O-core IR artifact)
        -> O-core target codegen + native linking -> executable binary

In this objective, "bundling runtimes with scripts" means a complete compiled program in binary or IR form, including OIR. The binary form contains O-core-generated native runtime/compiler code and the required scripts, libraries, modules, adapters, and data. A complete OIR program artifact contains the orchestration plan and verified native O-core code modules, with their realization bindings, linkage, script data, ABI, resources, execution profile, and provenance. Native module references must resolve to included verified content; references to an unavailable engine or missing dependencies do not constitute a complete bundle. A native O-core IR artifact is also a valid output when it includes the program and complete dependency and execution information needed for later native lowering. Neither IR form may require an ambient original runtime/compiler executable to supply missing engine code. The native orchestrator must have an explicit OIR/ExecutionPlan-to-O-core lowering path; carrying the logical plan does not implement that path. These complete runtime-bearing IR artifacts are not implemented yet. The bounded implementation bridge below is the first part of automated lowering. The existing olangc --target ir prints orchestration inspection output; it does not produce a complete runtime-bearing OIR or native O-core IR artifact.

The import path should reuse existing implementation-language frontends and build metadata, for example through LLVM IR or WebAssembly, rather than require each runtime to be manually rewritten in .oc. Generating O-core source in a polyglot staging block does not meet this automated lowering objective. Imported arithmetic, memory, ABI, and exception semantics must be preserved explicitly rather than assumed to match .oc. The importer must reject unsupported features with diagnostics. Native code produced by another compiler without O-core lowering does not qualify, nor does an unchanged imported module executed by an embedded IR interpreter.

Acceptance requires an actual complete external runtime or compiler implementation to enter O-core IR, pass verification, and produce native code through each of the three O-core emitters. Required functions, globals, initializers, relocations, ABI features, libraries, compiler helpers, and modules must be accounted for. A partial import or a feature-census percentage does not establish this acceptance criterion. The build must identify its source, configuration, frontend, IR, native artifacts, and complete declared import/data/library closure. Runtime reference tests and .O execution must verify results and required effects on each ISA after the original runtime inputs are removed and ambient runtime executable lookup is unavailable. Full runtime acceptance runs on native OSTADIX services, potentially through its native ABI personality. Linux-hosted compilation, user-mode emulation, and source capture provide development evidence; a Linux guest or host OS does not supply the services for that acceptance gate. Compiling a runtime does not itself implement them.

The foreign scripts may remain interpreted by the compiled runtime: compiling CPython's implementation and carrying Python scripts is a valid runtime compilation model. OIR still owns orchestration and OValue crossings; O-core MIR owns native computation. A complete OIR artifact can combine these layers while their internal representations retain their own invariants. Dynamic O.eval requires a resident O evaluator or an explicitly qualified compiled subset. Rewriting that evaluator in .oc and self-hosting the compiler are separate milestones and do not gate the first runtime importer. Compiling a compiler implementation does not redirect its output by itself; the programs it generates also need an explicit frontend/backend interface into O-core. Both capabilities belong to the overall compiler objective. For Rust, the acceptance target includes the original rustc implementation, LLVM backend, standard library, Cargo and their complete required dependency closure. It requires actual native compiler invocations and an O-core path for the programs they generate on all three ISAs. The scalar Rust fixtures are backend QA; they do not replace this unfinished compiler acceptance target.

The current runtime bundle feature embeds supplied runtime files. It does not implement this source-to-O-core compilation path.

Implemented native import boundary

ocore-native-module-v1 is a serializable, self-contained typed module with frontend target layout, functions, globals, direct aliases, initializers, symbol relocations, control-flow graphs, SSA values, and source/tool provenance. The LLVM importer uses the digest-pinned LLVM C API and a bitcode-record audit, then the independent Rust verifier checks the entire normalized inventory, including unused bodies. It checks types, dominance, exact phi predecessors, signatures, layouts and relocations before an ISA emitter receives the module. A structural verification receipt binds the exact module SHA-256; it does not establish emitter coverage, dependency closure, or native execution.

cargo build --locked --bin ocorec --bin olangc
target/debug/ocorec implementation.ll --input-kind llvm-ir --emit mir -o implementation.json
target/debug/ocorec implementation.json --input-kind native-ir --verify-native --receipt verification.json
target/debug/ocorec implementation.json --input-kind native-ir --target riscv64-unknown-none -o implementation.o

Generate frontend IR separately for each ISA. Preserve the original frontend triple, DataLayout and ABI: x86-64 IR cannot be made RISC-V input by changing the output flag. The default parser is the pinned Rust 1.97.1 LLVM 22.1.6 library; an explicitly selected library requires --llvm-library PATH --llvm-sha256 HASH. Clang assembles O-core's emitted assembly; it does not generate imported implementation machine code. The importer worker is embedded in ocorec and requires Python 3 on the build machine, independently of any compiled engine.

The current ISA profile implements every scalar integer width 1 through 64, ordinary pointers, fixed integer/pointer C and LLVM fastcc calls with scalar or aggregate values, including indirect and stack-passed calls, typed struct/array SSA values and storage, globals, byte-offset GEP, loads/stores, static entry-block allocations, branches, typed integer switches, parallel phi transfers, select, freeze, lifetime markers, and dynamic byte memory fill/copy/move operations. Zero-length memory operations perform no accesses; overlapping moves preserve the source byte snapshot. Switches retain every case and default edge, including shared destinations; verification compares exact numeric bit patterns for duplicate cases. Its llvm_defined_behavior_v1 contract preserves defined frontend behavior and records deterministic refinements of poison/undef and erased optimizer restrictions. LLVM assumptions remain explicit IR operations and are verified; the unoptimized emitter does not use them to change computation. Intrinsic declarations remain in the source inventory and cannot escape as native addresses. This contract is distinct from .oc integer division and shift semantics.

The imported scalar llvm.smin.iN, llvm.smax.iN, llvm.umin.iN and llvm.umax.iN families use one typed integer_min_max NativeIR operation. For the current realization, N is the original integer width from 1 through 64, and both arguments and the result must have that exact type. Signed selection compares values at their declared width before narrowing the result; signed i1 therefore treats the bit 1 as minus one. Each operand is materialized once. This preserves defined source results and uses the same recorded poison/undef refinement policy as the other imported scalar operations. It does not change .oc arithmetic rules.

Every intrinsic declaration, including an unused one, must have its canonical name and exact nonvariadic T(T, T) signature. Intrinsic bodies, address escapes, vector forms and widths outside the current scalar realization reject the whole module. These restrictions describe current coverage; the upstream LLVM operations also support wider integers and vector types.

Imported LLVM atomic loads, stores, fences, read-modify-write operations and compare-exchanges have separate typed NativeIR operations. Import preserves the original ordering, alignment, volatility, weak-CAS flag and context-local synchronization-scope ID. The module includes the original scope table with raw name bytes. LLVM's built-in system scope has an empty name; a custom scope named system remains a custom contract. Structural verification checks every atomic instruction, including unused functions and cold blocks, independently of whether the ISA emitter supports its realization.

Native atomic emission requires an explicit ordinary coherent-RAM profile:

target/debug/ocorec implementation.ll --input-kind llvm-ir \
  --atomic-profile coherent-ram-v1 --emit mir -o implementation.json
target/debug/ocorec implementation.json --input-kind native-ir \
  --target riscv64-unknown-none -o implementation.o

olangc --native-runtime CAPTURE --atomic-profile coherent-ram-v1 forwards the same contract to every required imported unit and verifies the returned profile. This profile excludes device memory. RV64 subword RMW/CAS also requires the entire aligned containing word to be accessible coherent RAM and the execution environment to provide the LR/SC eventuality property for that region. The profile declaration does not establish starvation freedom or physical memory-order qualification.

The current emitter supports naturally aligned i8/i16/i32/i64 and integral AS0 pointer atomics in the built-in system and single-thread scopes on all three ISAs. All fifteen integer RMW kinds are implemented. Compare-exchange retains its original {T, i1} old-value/success result; weak CAS is realized with a permitted strong retry. LLVM 22 accepts all fifteen combinations of the five success orders and three failure orders, including a failure order stronger than success. The hardware realization combines those requirements; it does not apply the separate .oc CAS ordering restriction.

Value width is checked independently of padded allocation size. Underaligned, wider, floating-point or custom-scope atomics that lack a supported realization reject the whole module before assembly output. They are not replaced by byte stores, erased fences or invented provider symbols. The scalar reference interpreter rejects atomic execution explicitly. Compiler conformance tests and platform qualification remain separate from complete upstream runtime or compiler lowering and dependency admission.

Integer operations normalize to their declared width. Every legal LLVM shift count is preserved, including non-power-of-two widths; poison-producing overshifts remain a separately recorded refinement. Ordinary memory accesses touch ceil(width/8) bytes even when LLVM allocation stride is larger, such as an i21 value with three stored bytes and four-byte allocation stride. Loading an unusual integer width requires the frontend's defined prior-store contract; unused high padding bits are unspecified. Odd three/five/six/seven-byte volatile loads and stores reject the complete unit because byte splitting does not establish equivalent volatile access semantics. The six LLVM signed/unsigned add, subtract and multiply overflow intrinsics retain both their width-normalized result and independent representability flag for every width 1 through 64. Signed one-bit multiplication keeps its mathematical overflow behavior: multiplying two negative one values overflows. Their original typed intrinsic declarations remain in the complete inventory. Aggregate constants retain their recursive types, including zero, empty, undef/poison and nested pointer or symbol-offset leaves. Typed extractvalue and insertvalue preserve their complete index paths. Aggregate phi, select and freeze operate on the scalar leaves; parallel phi transfers snapshot every incoming leaf before replacing any destination, including cyclic swaps. Ordinary aggregate loads and stores use the original DataLayout field offsets, array allocation strides and access alignment, including packed pointer fields. Padding is not an SSA value and is not promised to retain a particular byte pattern after an aggregate store. Empty structs and zero-length arrays have no value leaves or ordinary memory accesses; their type alignment remains part of surrounding layouts. Volatile aggregate accesses remain explicit in imported IR but reject native emission. Fixed C and LLVM fastcc call plans retain the original frontend's recursive integer/pointer parameter and result types, extension attributes, register-block placement, stack arguments and implicit result storage. Source-language aggregate coercions remain those of the original frontend; they are not reconstructed from a struct's byte size. byval, floating-point call classification and variadic calls remain explicit unsupported whole-unit contracts. Typed LLVM sret keeps a void result and its original pointer parameter in the first or second position. The signature records the sized in-memory result type as return_storage; declarations, definitions, calls and alias bindings must agree. x86-64 and RV64 keep the pointer in its ordinary argument position; AArch64 passes it in x8 while ordinary arguments use their own register/stack sequence. x86-64 restores the original result pointer in rax on every return, including after nested calls. Result-pointer metadata performs no initialization or memory access by itself, and sized empty result types remain valid. The scalar RV64 profile also preserves explicit lp64d frontend ABI metadata and the actual ELF double-float ABI flags; this admission does not qualify floating-point computation or aggregate register classification.

PIC/PIE flags are admitted only under a recorded static, nonpreemptive image contract. Symbol visibility remains explicit: default, hidden and protected definitions and declarations retain their ELF visibility, and closure combines the strongest reference constraint. This does not qualify dynamic interposition or shared-library loading. Defined-function LLVM UWTable requirements are preserved by the instruction-precise call-frame metadata described below. Ordinary declaration Sync/Async requests retain their parsed level and source site in provenance, together with the original declarations, calls and dependencies. Consumer objects emit call-frame entries for their own defined functions; external provider unwind tables and exception services require separate qualification. The static Itanium/DWARF exception profile below preserves recognized personalities and EH operations. Other EH models and unsupported surviving callsite or intrinsic unwind requests reject the whole unit. The importer records the original input digest and the pinned parser's normalized attribute values.

Local constant tables may retain 32-bit relative initializers with explicit target symbols and signed addends. Their base is the containing private or internal non-TLS global; targets may be ordinary globals, functions or direct aliases. Same-section differences retain exact resolved bytes, while other entries use x86-64 PC32, AArch64 PREL32 or paired RV64 ADD32/SUB32 relocations. The source llvm.load.relative.i32 and .i64 declarations remain in the whole inventory. Their calls lower to signed byte-offset addressing, a four-byte load, sign extension and addition to the original base. This is the static, nonpreemptive image profile; it does not qualify dynamic interposition or every image-range/code-model combination.

LLVM weak function and global definitions retain their bodies, initializers, relocations and actual ELF weak bindings. Symbol closure selects a compatible strong definition over weak definitions, or the first weak definition in the supplied module order. Every candidate must have the exact ABI/storage contract and sufficient selected-provider alignment, including overridden definitions. The original build's ordered link membership is separate evidence; a supplied module order alone does not qualify complete runtime linking. linkonce, linkonce_odr and weak_odr definitions and direct aliases retain their exact linkage names and ELF weak bindings. extern_weak declarations, common and available_externally definitions remain unsupported whole-unit contracts.

ELF any and nodeduplicate COMDAT groups keep code, globals and their relocation sections together. Direct aliases inherit their included root's group. Selection occurs before ordinary symbol resolution: the first any group wins in supplied module order; every nodeduplicate group remains, including when an any group uses the same signature. Nongroup definitions from losing modules remain. Object admission checks actual group signatures, flags, member sections and relocation targets against the verified module. Unsupported ELF selection policies such as exactmatch, largest and samesize reject the whole unit rather than changing the selection rule.

Direct aliases retain distinct names for existing code or storage in the same module. The alias value type must exactly match its defined function or global; alias calls inherit the function's complete ABI contract. Aliases keep their own linkage and visibility, address operands and relocations, without copying bodies or data. A strong replacement for a weak root name does not retarget an alias that still names the original object position; replacing a weak alias does not replace its strong root. Alias chains, surviving constant expressions, nonzero offsets, type casts, TLS, IFUNC and unresolved targets remain unsupported whole-unit contracts.

Alignment import retains the full LLVM maximum of 2^32 bytes even when the uint32 C API accessor returns zero. Audited bitcode preserves symbol alignments; mandatory alloca/load/store alignments retain that maximum without substituting a default. Native emission rejects an alignment it cannot realize before writing an artifact. Ordinary AS0 pointer results and fixed parameters may carry validated align, dereferenceable and dereferenceable_or_null promises. Their full-width payloads remain in provenance; native code does not optimize, allocate memory, speculate or add guards using these promises. The pinned LLVM reader/writer may normalize attributes, including dropping the maximum parameter alignment from serialized bitcode. Imports bind the exact original bytes and parsed contract; they do not invent a promise absent from the input module. Function alignment is explicit independently of signatures. Native definitions realize at least the requested alignment and the target's instruction alignment; unmaterializable definitions reject before emission. RISC-V modules disable assembler relaxation throughout the module so later aligned functions remain aligned without pending R_RISCV_ALIGN or R_RISCV_RELAX fixups. The source frontend and the assembler used for O-core's own code are recorded separately in the conformance receipts. Validated pointer-parameter readnone and dead_on_unwind promises and function/callsite allockind descriptions are recorded and erased without removing bodies, calls, memory operations or dependency symbols. Their presence does not establish purity, substitute an allocator or implement unwinding. Unsupported placements, payloads and actual ABI or exception-handling features still reject the whole unit. Validated function and callsite allocsize promises retain their exact raw LLVM payload and zero-based element/count parameter indices. The reserved count sentinel means no count parameter. Each referenced parameter must have a supported integer type, and the result must retain the supported pointer contract. Normalization erases this optimization promise while retaining every original call, body, memory access and dependency. It does not imply a fresh allocation, non-null result, pointer uniqueness, purity or an allocator replacement. Unsupported companion contracts reject the complete unit, including unused definitions.

Literal integer-to-pointer constants preserve exact 64-bit integral AS0 address representations under LLVM's zero-extension rule. Source integers of widths 1 through 64 are compile-time constants: i8 -1 becomes 255 and i64 -1 becomes all ones, without adding unsupported executable integer widths. Initializers contain these literal bytes without relocations; verified instruction operands use the typed pointer_bits representation. Symbol and GEP initializer addresses retain real relocations. Constant GEP operands in executable SSA preserve the tracked symbol or direct alias and their signed 64-bit byte offset. Layout uses the source's struct, packed and array types; integral AS0 pointer arithmetic wraps at 64 bits. The emitter resolves the base address before adding the offset, including negative and extreme offsets. These address bits do not grant access outside valid storage. Surviving unsupported wide integer-to-pointer operands, nonintegral or nonzero address spaces and unresolved symbolic pointer arithmetic reject the whole unit. The pinned LLVM reader may already normalize a wider expression into null, poison or undef; supported parsed pointer contracts remain bound to the exact original input SHA-256. Literal address bits do not establish mapping or dereference validity.

Unsupported operations, ABI features or hidden bitcode fields reject the whole unit before code artifacts are written. Floating-point computation and call classification, byval, ordinary variadics, dynamic TLS/DSO loading, additional unwind models, general dynamic stack allocation, managed execution and runtime-generated code publication remain required work. Weak/common/ODR linkage is not silently converted into strong linkage, and unaligned wide volatile accesses are rejected where the emitter cannot preserve their required access width. Frames and outgoing arguments probe intervening stack pages; RISC-V long jumps do not assume a small control-flow graph. Imported functions emit DWARF call-frame information for their saved frame pointer and return address, including prologue, epilogue, and multiple-return states. Their fixed frame pointer anchors unwinding through stack probes and outgoing argument allocations. Call-frame information alone does not supply an exception personality or the native platform's unwinder. scripts/check_ocore_native_cfi.py independently decodes the actual object unwind rows at instruction boundaries for nine functions across the three ISAs, including stack probes, outgoing arguments and multiple returns. Nine deliberately corrupted metadata controls must be rejected. This gate checks call-frame metadata separately from exception handling and runtime execution.

The imported native IR admits the explicit itanium_dwarf_v1 exception model for static, nonpreemptive ELF images on all three ISAs. It retains direct and indirect invoke calls, their distinct normal/unwind edges, canonical landingpad {ptr, i32} values, ordered catches and exclusion filters, llvm.eh.typeid.for selector queries and resume. A null catch-all, cleanup selector zero and an empty exclusion filter remain distinct. Invoke results exist only on the normal edge; shared landing-pad PHIs retain their original predecessors. Each emitted invoke landing entry saves the exception pointer and selector before PHI scratch moves, then discards outgoing arguments using the fixed frame pointer. Fixed entry allocations support alignment through 16 bytes; this profile does not admit dynamic allocas.

Personality references and LSDA/typeinfo table pointers use full 64-bit absolute relocations. CIE/FDE ranges, call-site intervals, ordered action chains, reversed type tables and filter byte offsets remain source-bound. EH-derived sections and relocations stay attached to their source any or nodeduplicate COMDAT groups. Metadata-only source i32 (...) personality declarations retain their original signature and require the separate five-argument C unwinder callback ABI at closure. Ordinary address uses, including cold code, aggregate constants, aliases and initializer relocations, remove that exemption. Actual resume operations require the typed external _Unwind_Resume interface; no provider implementation is invented. Production object admission checks these tables, symbol identities and relocation contracts against the verified IR. Its CFI instructions remain structural evidence; production admission does not execute CFA rows or establish machine code equivalence. Other EH models, arbitrary personality signatures, dynamic interposition and JIT table publication remain required work.

Imported execution profiles and cross-ISA equivalence

The following requirements describe the intended import design; they are not implemented runtime admission, snapshot, or JIT features.

Lowering, dependency closure, enforcement, and replayability are separate properties. Compiling a runtime through O-core does not establish that its clock, entropy, filesystem, scheduling, or CPU-dependent behavior is deterministic. Purity belongs to an operation and its admitted effects, not to a runtime name. Recording capability results would require a separately specified replay protocol; granting a capability alone does not record its results or make effects safely repeatable.

The required cross-ISA contract compares observable values, faults, and required effects under the same inputs and declared execution profile. For a profile admitting pure deterministic execution, this includes bit-identical canonical results across x86-64, AArch64, and RV64GC. Such a profile must specify floating-point rounding, contraction, subnormals, NaN behavior, and the libm implementation and CPU dispatch policy. Carrying one library source is insufficient if its compiled variants produce different results. Resource limits and host import behavior are also part of the profile. Neither a pinned Wasm module nor a C frontend plus libc proves this contract by itself.

Imported semantics remain explicit. Adopting Wasm rules for a Wasm importer does not change the existing .oc integer rules or establish C semantics. Record relevant source-build choices such as plain char signedness and signed-overflow flags. LLVM input carries target data layouts, calling conventions, variadic representations, and possibly target-specific intrinsics or assembly; x86 LLVM IR is not automatically portable input for the other two ISAs. A frontend/importer must obtain or normalize the required target contracts. The existence of O-core asm! does not establish support for foreign assembly constraints.

Dependency derivation may compute a sound over-approximation, including declared modules and extensions, because runtime-computed import names need not be exactly predictable from a script. The artifact must distinguish this declared closure from measured execution coverage. A census of a runtime's core functions does not qualify its external libraries, extension modules, or complete execution profile.

JIT runtime implementations remain within the compiler objective. A static executable-closure profile may forbid new executable code. A dynamic profile would instead require generated programs to pass through verified O-core lowering and controlled code publication, with provenance, relocations, imports, and code lifetime recorded. Compiling an existing native-code emitter does not automatically redirect the code it generates through O-core.

Per-image function tables are a possible imported representation, not a replacement for the current native C ABI. Table indices alone are forgeable integers; bounds and signature checks do not confer entry-specific authority. They also do not make a runtime heap portable by themselves. Cross-ISA snapshots require a defined data-pointer representation, object and allocator layouts, initialization state, and handling of host resources in addition to code references. Snapshots are an optional startup optimization, not evidence of runtime-source lowering.

2. Source units and modules

Every source file begins with a module declaration:

module kernel::serial;
use kernel::arch::outb;

An invocation of ocorec is one compilation unit and may contain multiple files. Module names must be unique. Unqualified names resolve in this order: local bindings, items in the current module, explicitly imported items, and predeclared intrinsics. Cross-module symbols are mangled unless marked @export or @no_mangle.

3. Items and control flow

The item forms are functions, extern functions, structures, enumerations, constants, and statics:

struct Slice { data: *const u8, len: usize }
enum Poll { pending, ready(u64), failed(i32) }

const PAGE_SIZE: usize = 4096;
static mut NEXT_PAGE: usize = 0x0020_0000;

extern "sysv64" fn boot_info() -> *const u8;

@export
@link_section(".text.kernel")
unsafe fn kernel_main() -> never {
    loop { asm!("hlt", options(nomem, nostack)); }
}

Statements include let, assignment, expression statements, if/else, while, loop, break, continue, return, and unsafe blocks. Functions have lexical scope and no implicit fallthrough return unless their return type is void.

Expression operands are evaluated from left to right: a call evaluates its target before its arguments, and indexing evaluates its base before its index. Aggregate initializer expressions follow their written order, including named structure fields written in a different order from their storage layout. A never expression ends its execution path immediately; enclosing calls, initializers, and returns do not evaluate later operands. Logical && and || evaluate their right operand only when required by their left operand.

4. Types

Primitive types are:

bool
u8 u16 u32 u64 usize
i8 i16 i32 i64 isize
f32 f64
void never

Compound types are arrays [T; N], immutable and mutable raw pointers *const T and *mut T, structures, enumerations, and function pointers fn(T, U) -> R or ABI-qualified extern "C" fn(T, U) -> R.

An array repeat [expr; N] evaluates expr exactly once, including when N is zero. Each element receives that value. Aggregate repeats first capture a private snapshot and copy it to the elements, so writes during copying cannot change the repeated value.

There are no implicit numeric conversions except that an unsuffixed integer literal may be inferred from its expected integer type. All other conversions use as. Data-pointer-to-integer, integer-to-pointer, pointer arithmetic, pointer dereference, mutable static access, inline assembly, and privileged intrinsics require an unsafe context.

Extracting a function's integer address is safe. Converting an integer or data pointer into a function pointer requires an unsafe context, as does changing a function pointer's signature or ABI.

Function pointers retain the target ABI and parameter/result types. They may be stored, assigned, and called indirectly; each indirect call requires an explicit unsafe context because its type does not carry the target's unsafe or effect contract:

unsafe fn invoke(callback: extern "C" fn(u64) -> u64, value: u64) -> u64 {
    return callback(value);
}

Function references are relocatable constants, including in static dispatch tables and aggregate initializers:

extern "C" fn foreign_step(value: u64) -> u64;
static DISPATCH: [extern "C" fn(u64) -> u64; 1] = [foreign_step];

Floating-point types reserve storage layout; x86_64's internal O-core ABI also permits bit-preserving transport. AArch64/RISC-V float parameters and returns remain unsupported even with the O-core ABI. Float literals, arithmetic, comparisons, casts, indirect float calls, and C/sysv64 float parameters and returns are compile-time errors. Target floating-point instructions and calling conventions remain future work. This boundary is enforced in type checking and defended again in machine code generation.

Integer results are narrowed to their declared width after each operation. Shifts operate on the sign- or zero-extended 64-bit operand with the count modulo 64, then narrow the result; signed right shifts are arithmetic. Division and remainder trap on a zero divisor and on signed 64-bit minimum divided by -1. Narrow signed minimum divided by -1 is computed in 64 bits and wraps when narrowed. These rules are shared by all three backends.

Boolean values are normalized to 0 or 1. Casting an integer to bool produces false for zero and true for every nonzero source value, including values whose low byte is zero. Boolean memory loads and assembly outputs also normalize nonzero values to true. A Boolean call result uses its declared low byte before normalization; undefined upper ABI register bits do not change the result.

O-core v0.1 has no garbage collector and no implicit heap allocation. Values have deterministic destruction-free storage. A later ownership layer may add checked owning pointers, but it must lower to this explicit storage model.

5. Layout and ABI

Primitive sizes and alignments are identical on the three supported targets:

Type Size Alignment
bool, u8, i8 1 1
u16, i16 2 2
u32, i32, f32 4 4
u64, i64, usize, isize, f64, pointer 8 8
void, never 0 1

Structures use declaration order. Each field begins at the next address aligned for that field; structure size is rounded up to maximum field alignment. @packed removes inter-field padding and gives alignment 1. @align(N) may increase alignment to a power of two up to 4096. Local frames honor that alignment while preserving incoming stack arguments and the target's callee-preserved registers. Packed scalar fields support unaligned ordinary loads/stores. Large local frames and arguments beyond the register set are supported; execution still requires enough actual stack storage.

Enums are a tagged union. The tag is the smallest of u8, u16, or u32 that can represent every variant. The payload begins at its required alignment after the tag; total size is rounded to maximum tag/payload alignment.

extern "C" supports non-variadic integer, Boolean, pointer, and function-pointer arguments and scalar results, for declarations and function definitions with bodies. Register overflow arguments travel on the stack in both direct and indirect calls, with 16-byte call alignment and correct incoming/outgoing narrow scalar extension:

Target Integer argument registers Scalar result C ABI
x86_64 RDI, RSI, RDX, RCX, R8, R9 RAX System V AMD64
AArch64 x0--x7 x0 AAPCS64
RISC-V RV64GC a0--a7 a0 RISC-V LP64 psABI

RISC-V C call/return boundaries apply the psABI's 32-bit sign extension even for u32; unsigned SSA values remain zero-extended internally. extern "sysv64" explicitly selects the AMD64 convention and is rejected on other targets. Aggregate parameters and returns are forbidden across direct and indirect calls, including extern calls; pass pointers instead. Variadic calls and floating-point C ABI classification are not implemented.

extern "ocore" is versioned with the compiler and is not a stable foreign ABI. Interrupt entries use the x86_64-only @interrupt; they have no ordinary arguments or return value and end with iretq. AArch64/RISC-V trap-frame glue must be explicit operand-free @naked assembly.

Aggregate assignment has memmove semantics, including overlap and identical source/destination addresses. MIR phi values are assigned simultaneously on each incoming control-flow edge, including loop-carried cycles.

6. Unsafe and hardware operations

Unsafe operations are syntactically visible:

unsafe {
    volatile_store(mmio, value);
    let status: u32 = volatile_load(status_reg);
    outb(0x3f8, byte);
}

Freestanding intrinsics are:

  • volatile_load(ptr) and volatile_store(ptr, value);
  • atomic_load(ptr, order), atomic_store(ptr, value, order), atomic_exchange, atomic_compare_exchange, and atomic_fetch_add;
  • inb, inw, inl, outb, outw, outl;
  • enable_interrupts, disable_interrupts, halt, and invalidate_page;
  • syscall0 through syscall6 for user-mode stubs;
  • asm!(template, operands..., options(...)).

Memory order values are relaxed, acquire, release, acq_rel, and seq_cst. Invalid load/release and store/acquire combinations are compile-time errors. Compare-exchange failure order cannot be release or acq_rel and cannot be stronger than its success order. Volatile operations prevent compiler elision and reordering relative to other volatile operations; they do not provide inter-core synchronization. The current volatile lowering accepts scalar pointees. Atomic pointees must be 1, 2, 4, or 8-byte integers on all three targets. Volatile scalar access and atomics require natural width alignment and explicitly trap on a misaligned address on every target. Ordinary packed loads/stores remain valid, and aggregate copies transfer bytes. Each backend rechecks pointer, value, result, and ordering types. RISC-V subword read-modify-write uses masked word LR/SC loops and may provide stronger ordering than requested.

Inline assembly templates use the selected target's assembler syntax (Intel syntax on x86_64). Input/output registers are explicit. Non-naked templates must restore the stack pointer and preserve the target's reserved frame and platform registers; this is the unsafe assembly author's contract. options(nostack) asserts that the target stack pointer is unchanged. Assembly operands must be non-floating scalar values because the current interface exposes general-purpose registers. Assembly is unsafe even when it contains no privileged instruction. Inputs are prepared together, and output registers are preserved before output-place address calculation, so scratch-register operands and indexed destinations retain their values.

7. Linkage attributes

Supported attributes are:

  • @export: externally visible symbol;
  • @no_mangle: use the source identifier as the linker symbol;
  • @link_section("name"): place a function or static in a named section;
  • @align(N): increase item/type alignment;
  • @used: retain an otherwise unreferenced static;
  • @packed: packed structure layout;
  • @interrupt: x86_64 interrupt entry ABI;
  • @naked: no compiler prologue/epilogue; body is restricted to assembly.

Section names are emitted verbatim. Applying executable section attributes to writable statics is rejected unless @unsafe_linkage is also present.

8. Freestanding runtime boundary

The freestanding runtime may depend only on the target ABI and symbols provided by the kernel image. It may not depend on subprocesses, JSON, filesystem access, Python, Nix, libc, Rust std, environment variables, or a host allocator.

The runtime supplies boot entry glue, zeroing .bss, serial I/O, IDT installation, a timer interrupt, fixed-window reclaiming frame allocation, syscall entry, and panic-to-serial. Allocation in interrupt context is forbidden until a separate interrupt-safe allocator exists. The current allocator is single-CPU and relies on boot and syscall entry running with interrupts masked.

9. Capabilities and syscalls

A generic or deserialized OCapability is not kernel authority. An OCapability emitted by a live hosted broker is a bearer for a private session binding. Kernel authority itself is represented by an unforgeable (slot, generation) handle tied to a per-process capability table:

CapabilityEntry = { object_id, object_type, rights, generation, state }
CapabilityHandle = (generation << 32) | slot

Every capability syscall validates slot bounds, live state, generation, object type, and requested rights. Handles never contain kernel pointers. Kernel-only transfer transactions can reserve a destination slot without exposing it as a live capability, then publish or abort that exact reservation. Close similarly uses a begin/commit/abort state. Committing a close or aborting an unpublished reservation advances its generation before reuse; aborting an in-progress close restores the same exact live capability. Exhausted 32-bit generations retire instead of wrapping to a value that could revive an old handle.

page_alloc accepts anonymous or shared memory from a typed page-pool capability. It enforces the current CSpace's hard frame quota and distinguishes quota exhaustion, physical-frame exhaustion, resource-table exhaustion, and an invalid memory kind. Executable memory remains kernel/loader-only; device memory is never allocated from the RAM pool. The returned value is a CSpace capability, not an internal object handle, frame index, or physical address.

yield records a request in every mode. It requests an actual scheduler transition when the Milestone 2 scheduler is active and returns directly in the bootstrap gate. exit abandons a user frame only after the kernel has installed a trusted lifecycle continuation. sleep rejects zero or out-of-range delays and returns ERR_NOT_IMPLEMENTED when the scheduler is inactive. It does not bind the endpoint object, and the receiver's CSpace slot remains kernel-selected. The public gate exhausts all 16 ticket records, denies abort by a non-owner process, lets the owner abort each once, rejects a stale repeat, and proves a fresh prepare succeeds afterward. Endpoint send/receive/cancel are public CPL3 operations with bounded copy and real scheduler block/wake behavior. The M5 serial operations require the exact typed control object installed only in the loaded REPL CSpace.

Mode 18 adds three M6A-only calls: scalar personality call, personality reply, and supervision. A generation-bound call capability routes the test personality's scalar operation and input through a kernel request record to an endpoint owned by the current unprivileged daemon. A typed reply capability is installed only in that daemon; a rotating typed supervision capability is installed only in the unprivileged supervisor. The request record arbitrates reply, supervisor cancellation, deadline expiry, and service death into one terminal state and one dependent wake. The test personality admits only its small scalar syscall whitelist; pointer-bearing endpoint operations return ERR_NOT_IMPLEMENTED rather than bypassing a future memory-view protocol.

The hosted OCapability wire value may refer to a live kernel capability only through an authenticated transport endpoint. Its string identity is never accepted directly as a kernel handle.

The hosted CapabilityBroker implements this boundary. It generates 256-bit bearer identities from operating-system entropy and keeps a private per-session token-to-handle table. Callers use operation-specific debug_write and cap_close methods; they cannot select a syscall number, expected kind, or required-rights mask. A successful kernel close removes the bearer, while a transport failure or kernel rejection preserves it. Deserialized identities not already bound in that live broker session are rejected as forged or stale. Metadata cannot select a slot or add rights.

This prevents guessing, serialized forgery, metadata-based escalation, stale or revoked token use, and cross-session replay. It does not prevent theft of a still-live bearer inside the same broker session, broker-process compromise, or authenticated-transport compromise. Possession of a live bearer is an explicit delegation of its bounded authority.

Foreign blocks remain part of .O orchestration. They may construct O-core source, invoke ocorec, link images, launch QEMU, and inspect results. 11. Implemented bounded O-core milestone boundary

The compiler supports x86_64, AArch64, and RV64GC native assembly/object generation. All three are stack-spill backends without optimization or a general register allocator. They implement scalar locals and pointers, integer operations and casts, direct and unsafe indirect calls with stack arguments, branches and parallel phi moves, volatile memory, all supported atomic integer widths, aligned local frames, and overlap-safe aggregate copies. Aggregates support layout, construction, fields, indexing, locals, and statics; call boundaries still require pointers to aggregates. Enum construction is supported; pattern matching is not. MIR structure and codegen type contracts are checked before unsupported shapes can select machine instructions. Floating-point computation and full C ABI classification remain unsupported.

Privileged operations remain architecture-specific. AArch64 implements DAIF masks, wfi, page invalidation, inline assembly, operand-free naked functions, and syscall0 through syscall6 using x8 and x0--x5. RISC-V implements supervisor interrupt masks, wfi, sfence.vma, inline assembly, operand-free naked functions, and ecall using a7 and a0--a5. Both reject AMD64 sysv64, x86 port I/O, and the x86 interrupt-entry ABI. The RISC-V compiler backend does not establish a RISC-V bootable kernel or runtime port.

The same-source execution gate builds .oc with the real ocorec CLI for all three targets, links an independent freestanding C reference harness, and executes x86_64 natively plus AArch64/RISC-V under QEMU user emulation:

python3 scripts/check_ocore_native_equivalence.py \
  --ocorec target/debug/ocorec --output-dir target/ocore-native-equivalence

Run it on an x86_64 Linux host with clang, ld.lld, qemu-aarch64, and qemu-riscv64 (qemu-user); missing tools fail the gate. The corpus checks 4096 vectors across three arithmetic functions (12,288 reference comparisons per ISA), C crossings in both directions, twelve-argument direct/indirect calls, packed and aligned memory, an 8193-byte local array, overlap-safe copies, volatile memory, and 8/16/32/64-bit atomics. Successful output bytes must agree across targets. Six separate fault programs per ISA must trap: four division/remainder cases and two misaligned volatile/atomic accesses. Object bytes must reproduce across output directories. Two additional executions verify that a never call inside an array repeat or an outer call argument exits immediately with the expected status. Retained artifacts include assembly, ELF objects/executables, and equivalence.json. This is compiler conformance evidence for the checked corpus, separate from kernel boot and subsystem proof.
